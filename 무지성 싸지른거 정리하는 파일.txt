# HoloCure Clone Project

WinAPI와 C++를 기반으로 제작한 HoloCure 클론 프로젝트입니다.

게임 루프, Scene 관리, ObjectPool, Signal(Event) 시스템 등을 직접 구현하며
게임 프레임 워크 구조와 객체 생명주기 관리에 대한 이해를 목표로 진행하였습니다.

## 주요 목표

- WinAPI 기반 게임 프레임워크 제작
- Scene 기반 객체 관리
- Object Pool 구현
- Signal(Event) 시스템 구현
- UI Framework 제작

## 기술 스택

- C++
- WinAPI
- GDI
- STL

## 디자인 패턴

- Singleton
- Observer Pattern
- Component Pattern
- Object Pooling

### FSM

#### 문제

상태 전환 시 애니메이션 변경 코드가 여러 곳에 흩어져 있었고
상태 변경 시 애니메이션 갱신이 누락되는 경우가 발생하였다.

#### 해결

상태를 변경 해주는 함수를 넣었다.
```
SetState(State state);
```

상태 전환은 해당 함수로만 이루어지게 하였고
상태 변경시 상태가 갱신이 되고 애니메이션 교체를 수행하도록 한다.

SetState 호출시
1. 현재 상태와 새로운 상태가 같은지 판별
2. 상태가 다를 경우 상태 변경
3. 애니메이션 변경

을 수행하도록 하였다.
(이 부분은 구조도로 바꾸는게 좋아 보인다.)

#### 결과

- 애니메이션 전환 누락 방지
- 호출 코드 단순화
- 디버깅 용이성 향상

{

### Object Pool

#### 의도

투사체나 몬스터 등 반복적으로 많이 사용되는 객체가 많아
이걸 일일이 생성 및 삭제가 이루어지는 비용이 들어
만들어 놓은 걸 재사용하는 것이 좋다고 판단하였고
미리 만들어 놓은 스톡이 부족하면 새로 추가로 만들게 구성을 하였다.

#### 문제

비활성 객체를 씬 내에서 들고 필요할때마다 앞에서 부터 활성화 하였다.
부족하면 새로이 만들고 하여 삭제 비용을 최소화 할려고 하였으나
비활성 객체가 씬에 계속 누적이 되며 순회하는 비용이 증가 하였다.

#### 해결

ObjectPool을 만들어서 비활성화 된 객체를 씬에서 제거하고
풀로 옮겨주고 씬의 순회 비용을 감소 시켜주었고
반대로 풀에 있던 객체를 꺼내서 씬에 다시 넣어줌으로써 객체를 새로 만드는 것이 아닌
기존에 있던 객체를 Reset 함수를 호출하여 초기화를 시켜주고 재사용하였다.

#### 결과

- 몬스터 재사용 가능
- 투사체 재사용 가능
- 동적 할당 감소

#### 특징

- 비활성 객체 재사용
- 기본 UI는 예외처리(BaseUI or 게임 종료 같은 상황이나 씬전환 같은 상황시 비활성화 되는 애들은 제외)
- Scene 반환 구조

### Signal

#### 문제

Signal 구독 시스템 구현 중 이벤트가 즉시 해제되는 문제가 발생

```
_expConn = move( player->OnExpChanged += ...	);

```

구독 직후 이벤트가 비정상적으로 끊어짐

#### 원인 분석

초기 구현은 Connection 이동 생성자가 실제 상태 이전을 수행하지 않았다.
```
Connection(Connection&&) noexcept
	{
		cout << "[DEBUG] Connection 이동 생성" << endl;
	}
```
들어오는지 확인하기 위해 내부 구현은 안하고 디버그 로그만 써놓음으로 인해
operator += 결과로 생성된 임시 Connection 객체가 이동 후 소멸되며
결과적으로 
```
~Connection() { Disconnect(); }
```
호출하게 되어 구독이 제거가 되었다.

#### 해결

- move semantics 수정
- Connection 생명주기 재설계
- shared_ptr<Node>, weak_ptr<Node> 도입
- Signal 파괴 시 dangling pointer 방지

#### 배운점

처음에는 smartpointer 도입으로 문제가 해결 되었다고 판단했으나,
이후 분석 과정에서 실제 원인이 move semantics와 객체 생명주기 관리였음을 확인하였다.
이 경험을 통해 포인터 종류보다 소유권과 객체 생명주기 설계의 중요함을 학습하였다.

### ObjectPool 초기화 중복 문제

#### 문제

ObjectPool이 객체 부족시 Factory를 통해 객체 생성
[Pool Empty -> Factory Create -> Init() -> 객체 return] 0

이미 초기화 완료 상태였으나 재사용시 추가 Init() 호출이 발생하였다.
	
#### 결과

컴포넌트 중복 생성
Collider 중복
Animation 중복
	
일어난 일 :
데미지 2회 적용
애니메이션 중첩 출력 발생

#### 원인

생성 책임 위치 혼동
[Factory : Create -> Init -> return] 0
이미 초기화가 완료된 상태
Pool 재사용시 추가 초기화를 불필요함

#### 해결

재사용하는 객체들 즉 투사체나 몬스터 같은 것들은 풀에 반환 될때 그 반환 함수 안에서
reset을 호출 reset을 재사용용 초기화
Init은 최초 생성 reset은 재사용 초기화로 역할을 분리하였다.

#### 배운 점

초기화 책임을 명확히 분리해야하고 분리기준을 명확히 할 것

## Retrospective

프로젝트를 진행하며 Scene 기반 객체 관리,
Object Pool, Signal(Event) 시스템 등을 직접 구현하면서
객체 생명주기와 의존성 관리의 중요성을 학습할 수 있었다.

특히 Signal 시스템 구현 과정에서 발생한 Move Semantics 문제를 분석하며
스마트 포인터 자체보다 객체의 소유권과 생명주기 설계가 더 중요하다는 점을 경험하였다.

향후에는 Engine / Content Layer를 더욱 명확히 분리하고
데이터 기반 장비 시스템을 도입하여 확장성을 개선할 예정이다.
