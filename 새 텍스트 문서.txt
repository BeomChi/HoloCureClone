HoloCure Clone Project (C++ / WinAPI)

이 프로젝트는 Kay Yu의 HoloCure 게임을 기반으로 직접 구현해보는 클론 프로젝트입니다.
C++ 및 WinAPI를 기반으로 게임 루프, 객체 관리, 시스템 매니저 등 게임 개발의 기초부터 직접 구현하며 학습하고자 시작했습니다.

본 프로젝트는 비영리적인 포트폴리오 목적으로만 제작되며, 상업적 사용은 일절 없습니다.
참고 리소스는 일부 원작 리소스를 기반으로 하고 있습니다.

목적
 - WinAPI 기반 게임 루프 및 프레임워크 구현
 - Scene / ObjectPool / UI 등 재사용 가능한 시스템 제작
 - 게임 객체 생명주기 관리 학습
 - Unity 스타일 구조 일부 직접 구현
 - 실제 게임 구조 분석 및 재구현

## 구조 개선 과정

초기:
ObjectManager 중심
모든 객체를 ObjectManager가 직접 관리하는 구조였다.

하지만 객체 수 증가와 함께 객체 생성 / 제거/ 생명주기 관리 책임이 집중되었으며
관리 범위가 점점 커지는 문제가 발생하였다.
예를 들어 타이틀 화면에 들어가는 오브젝트랑 실제 플레이하는데 필요한 오브젝트들
플레이하는데에 있어 타이틀 씬에 있는 오브젝트들은 필요가 없는걸 들고 있어
씬에서 매니저에 있는 것들을 순회할때 필요한 것뿐만아니라 더 이상 안쓰는 것들까지 순회를 해
순회하는 비용이 추가로 들어 각 씬에 필요한 오브젝트들을 매니저가 한번에 모아서 관리하는게 아닌 
각 씬들이 관리하는 편이 더 좋다고 판단을 하였고 그리하여 구조를 변경하게 되었다.

 FSM
  문제
	상태 전환 시 애니메이션 변경 코드가 여러 곳에 흩어져 있었고
	상배 변경 시 애니메이션 갱신이 누락될 가능성이 존재하였다.
  
  해결
	상태를 변경 해주는 함수를 넣었다.
	SetState(State state);
	상태 전환은 해당 함수 통해서만 이루어지게 하였다.

	상태 변경시 상태가 갱신이 되고 애니메이션을 교체를 수행하도록 구성하였다.

	SetState 호출 시
	1.현재 상태와 새로운 상태가 같은지 판별
	2. 상태 변경
	3. 애니메이션 변경
	을 함께 수행하도록 구성하였다.
	
  결과
	- 애니메이션 전환 누락 방지
	- 호출 코드 단순화
	- 디버깅 용이성 향상

Collider
	- 원본 -
	AABB를 이용하여 충돌체크를 만들었다.
	이걸 만든 이유는 거리비례로 충돌했는지 안했는지 판별을 하는 법도 있겠지만
	씬 업데이트 내에서 좀 업데이트 되는 걸 세분화 하고 싶었다.
	세분화라고 해도 유니티처럼 복잡하게는 무리일거 같고 이런 프로젝트에서
	그렇게까지 세분화해야할 필요성을 못 느껴서 게임 로직, 충돌 체크 이렇게 간단하게 나누었다.
	
의도
	게임 로직과 충돌 처리를 분리하기 위해 Collider 시스템 제작
	Sene Update 내에서
	Game Logic -> CollisonManager::Update -> Render
	순서로 처리하였다.

  구현
	AABB 충돌 판정 사용(임시 포트폴리오에 있는 그림 사용 예정)
	Box vs Box 로 충돌 여부 확인

  고찰
	프로젝트 규모상 Unity 같은 상용엔진 수준으로 세분화의 필요성이 느껴지지 않아 적용하지 않았다.
	게임 로직 / 충돌 처리 정도로 단순 분리하였다.
	만약에 물리연산을 넣게 된다면
	업데이트 -> 물리 연산 -> 뒤늦은 업데이트 -> 충돌 계산 이렇게 하지 않을까 싶다.


Camera
  의도
	맵 크기가 화면보다 크기 떄문에 플레이어 이동 시 카메락 추적 기능이 필요하였다.
	카메라 위치 기준으로 월드 좌표를 화면 좌표로 변환하여 렌더링하도록 구성하였다.

  구현
	초기에는 Component 구조를 고려하였다.
	하지만 Unity처럼 독립 GameOBject 구조가 더 적합하다고 판단하여
	(하지만 일단 컴포넌트는 남겨는 놓았다.)
	GameObject -> Camera 형태로 카메라가 GameObject를 상속 받은 형태로 변경하였다.

  기능
	Target 추적
	자유 이동
	World -> Screen 반환 혹은 Screen -> World

Vec2 SceneManager::WorldToScreen(Vec2 pos)
{
	return pos - _cameraPos + Vec2(GWinSizeX / 2, GWinSizeY / 2);
}

Vec2 SceneManager::ScreenToWorld(Vec2 pos)
{
	return pos + _cameraPos - Vec2(GWinSizeX / 2, GWinSizeY / 2);
}

  구조
	SceneManager가 현재 Scene 카메라 위치를 들고 있는다.
	렌더 시 : World Position -> Camera Offset -> Screen Position 변화을 수행한다.


 Object Pool
  의도
	투사체나 몬스터등 반복적으로 많이 사용되는 객체가 많아
	이걸 일일이 지우고 다시 만들고 하는 비용이 아까워
	만들어놓은 재사용하거 부족하면 그때 새로이 만든다는 생각에 풀을 도입

  문제
	비활성 객체가 씬에 계속 누적이 되며 순회하는 비용이 증가

  해결
	ObjectPool을 만들어서 비활성화 된 객체를 씬에서 제거하고
	풀로 옮겨주고 씬의 순회 비용을 감소 시킴 반대로
	풀에 있던걸 꺼내서 씬에 다시 넣어주므로 객체를 새로 만드는 것이 아닌
	기존에 있던 객체를 Reset 함수를 호출하여 초기화를 시켜주고 재사용

  특징 
	비활성 객체 재사용
	기본 UI는 예외처리(DamageText 같이 많이 필요한건 재사용해야해서)
	Scene 반환 구조

 Signal
  의도
	기존에는 클래스간 서로 들고 있어야 했는데 서로 헤더를 물고 있어서
	의존성이 올라가고 나중에 디버깅을 하거나 구조개편을 할때
	힘들어 질거 같아서 유니티의 이벤트처럼 신호만 주면 그에 구독된 애들한테
	알림을 주는 방식으로 하는 편이 좋다고 판단함
	
	예
	Plauer -> UI 직접 참조  x
	 └ Signal
		 └ UI 구독

	사용 사례
	HP 갱신
	EXP 갱신
	레벨업 UI
	장비 선택 UI

  특징
	Observer Pattern 기반
	Connection 구독 관리
	자동 Disconnect
	객체 결합도 감소

  기능

Scene
  문제
	업데이트 중 객체 추가 / 삭제가 발생하면
	Update 중 -> Object 삭제 -> 벡터 변경 -> 잘못된 포인터 접근 Iterator 무효화
	문제가 발생하였다.

	객체 제거 이후 이미 제거된 객체 접근이나 잘못된 위치 접근으로 크래시가 발생하였다.

  해결
	예약 시스템 도입
	Update 중 삭제 요청 -> PendingRemove Update 중 추가 요청 -> PendingAdd
	-> Logic 종료 -> Remove 적용 -> 다음 Frame -> Add 적용
	즉시 추가 / 삭제를 수행하지 않고 프레임 뒤로 미루는 방식으로 처리하였다.

  결과
	Iterator 무효화 방지
	생명주기 안정화
	Update 중 안전한 생성 / 삭제 가능



Signal
  문제
	Signale 구독 시스템 구현 중 이벤트가 즉시 해제되는 문제가 발생

	_expConn = move(
  	  player->OnExpChanged += ...
	);
	구독 직후 이벤트가 비정상적으로 끊어짐

  원인 분석
	초기 구현은 Connection 이동 생성자가 실제 상태 이전을 수행하지 않았다.
	Connection(Connection&&) noexcept
	{
		cout << "[DEBUG] Connection 이동 생성" << endl;
	}

	들어오는지 확인한다고 내부 구현은 안하고 디버그 로그만 써놓음
	operator+= 결과로 생성된 임시 Connection 객체가 이동후 소멸되며

	~Connection() { Disconnect(); }

	소멸자 내 Disconnerct()가 실행되어
	구독이 제거되었다.

  해결
	move semantics 수정
	Connection 생명주기 재설계
	shared_ptr<Node>, weak_ptr<Node> 도입
	Signal 파괴 시 dangling pointer 방지.

  배운점
	처음에는 smartpointer 도입으로 문제가 해결되었다고 판단했으나, 이후 분석 과정에서
	실제 원인이 move semantics와 객체 생명주기 관리였음을 확인하였다.
	이 경험을 통해 포인터 종류보다 소유권과 객체 생명주기 설계가 중요함을 학습하였다.
	

월드 좌표 / 스크린 좌표 문제

  문제
	DamageText가 화면에서 비정상적으로 이동하였다.

  원인
	월드 좌표와 화면 좌표를 혼합하여 사용하였다.
	카메라 이동 시 좌표 차이가 발생하였다.

  해결
	렌더링 시 카메라 기준 좌표 변환을 적용하였다.
	ScreenPos = WorldPos - CameraPos;

  고찰점
	GDI의 TextOut이나 TextRender가 많이 무거워서 프레임 방어가 어렵다
	그래서 현재 숫자 비트맵을 통해서 데미지를 출력하는 방식으로 바꿀까한다.
	아니다 지금 버전과 비트맵 적용버전의 프레임 차이를 보여주는게 더 좋을거 같다.

ObjectPool 초기화 중복 문제
  문제
	ObjectPool이 객체 부족시 Factory를 통해 객체 생성
	Pool Empty -> Factory Create -> Init() -> 객체 return

	이미 초기화 완료 상태였으나 재사용시 추가 Init() 호출이 발생하였다.
	
  결과
	컴포넌트 중복 생성
	 Collider 중복
	 Animation 중복
	
	일어난 일 :
	 데미지 2회 적용
	 애니메이션 중첩 출력
	발생

  원인
	생성 책임 위치 혼동
	Factory : Create -> Init -> return
	이미 초기화가 완료된 상태
	Pool 재사용시 추가 초기화를 불필요함

  해결
	재사용하는 객체들 즉 투사체나 몬스터 같은 것들은 풀에 반환 될때 그 반환 함수 안에서
	reset을 호출 reset을 재사용용 초기화
	Init은 최초 생성 reset은 재사용 초기화로 역할을 분리하였다.

  배운 점
	초기화 책임을 명확히 분리해야하고 분리기준을 명확히 할 것
